## Summary

결제 실패 주문을 `payment_failed` 상태와 실패 이력으로 보존하고, 관리자 주문 목록에서 운영에 필요한 실패 정보를 확인할 수 있게 한다. 재고 관련 요청은 결제 실패·재결제 거부 시의 재고 불변만 이 초안의 확정 범위에 포함하며, 나머지 시나리오는 미정으로 남긴다.

## Context

입력은 결제 실패 처리, 관리자 노출, 재고 문제의 신속한 해결을 요청한다. 요청에는 재현 조건, 관리자 노출의 API/UI 범위, 재고 시나리오, 응답 스키마가 없다. 이 초안은 세 정책에서 확정된 결제 실패 경계를 정리하며, 정책상 보류됐거나 요청에서 특정되지 않은 내용은 구현 대상으로 정하지 않는다.

## Current Behavior

- `OrderStatus`에는 `payment_failed`가 없고, `POST /orders/:id/pay`의 `FAIL`로 시작하는 카드 토큰 결제 실패는 실패 시도를 기록한 뒤 주문을 삭제하고 HTTP 200과 `{ ok: false }`를 반환한다.
- `GET /admin/orders`는 남아 있는 주문만 순회하므로 삭제된 실패 주문을 표시하지 못한다. 현재는 실패 시도가 있으면 저장된 상태대신 `결제실패`를 파생해 표시하며, 실패 사유를 저장하지 않는다.
- 주문 생성 시 재고를 즉시 차감하며, 동일 상품 수량 합산과 재고 부족 검사가 없다. 현재 테스트는 실패 주문 보존·상태·재고·상세 응답을 검증하지 않는다.

## Expected Behavior

- `pending` 주문의 결제 실패는 `payment_failed`로 전환하며, 주문과 해당 실패 결제 시도를 보존한다.
- 결제 실패는 HTTP 402와 안전한 실패 정보를 반환하며, 카드 정보·내부 오류·예외 메시지·스택·원시 오류 응답을 노출하지 않는다.
- 같은 `payment_failed` 주문에는 새 결제를 시도하거나 성공 처리하지 않는다. 거부 후 주문 상태·결제 이력·재고는 변경되지 않는다.
- 관리자 주문 목록은 보존된 `payment_failed` 주문을 포함하며, 실제 저장 상태를 `payment_failed`로 표시한다. 해당 주문에만 실패 금액·시각·안전한 사유를 제공하며, 일반 주문에는 실패 정보를 붙이지 않는다.
- 주문 생성 시 재고 부족 차단, 생성 시 미차감, 결제 성공 직전 재검사와 1회 차감은 정책상 승인됐으나, 이 Issue에 포함할 세부 재고 시나리오는 **미정**이다.

## Scope

### 확정된 범위

- 결제 실패의 `pending → payment_failed` 상태 전환, 실패 주문·결제 시도 보존, HTTP 402 응답
- `payment_failed` 주문의 재결제 거부와 거부 후 상태·이력·재고 미변경
- 보존된 실패 주문의 관리자 주문 목록 노출 요건과 실패 정보의 조건부 제공
- 위 행동의 상태·응답·저장 결과를 검증하는 테스트

### 미정 범위

- 요청의 “관리자 화면”을 기존 `GET /admin/orders` API로 완료로 볼지, 별도 UI를 제작할지
- “재고 문제”에서 주문 생성 부족·동일 상품 합산·생성 시 미차감·결제 성공 재검사·중복 차감중 무엇을 포함할지
- 결제 시점 재고 부족의 주문 상태와 결제 응답

## Out of Scope

- `cancelled`·`refunded` 흐름, 환불 API와 환불 후 재입고
- 네트워크·인프라 수준 재시도의 허용 조건, 식별 방식, 횟수 제한
- 새 관리자 UI를 제작하는 일—관리자 화면 범위가 확정되기 전에는 포함하지 않음
- 실결제 제공자와의 연동, 실거래 결제 처리

## Acceptance Criteria

### 확정된 범위

- [ ] 상태: `pending` 주문에 실패 결제를 시도한 후, 주문 조회 결과의 `status`가 `payment_failed`이다.
- [ ] 응답: `pending` 주문에 실패 결제를 시도했을 때 HTTP 상태가 402이다.
- [ ] 저장 결과: 결제 실패 후 주문은 저장소에 남아 있고, 해당 주문 ID·실패 결과·금액·시각을 가진 결제 시도 이력이 보존된다.
- [ ] 재고: 결제 실패 후 해당 주문 품목의 재고 수량이 결제 시도 직전의 수량과 같다.
- [ ] 재결제 거부: `payment_failed` 주문에 다시 결제를 요청한 후, 주문 `status`는 `payment_failed`로 남고 결제 시도 이력 개수와 재고 수량은 요청 직전과 같다.
- [ ] 관리자 목록: 실패 주문이 관리자 주문 목록에 포함되고, 해당 행의 상태가 저장된 `payment_failed`로 표시된다.
- [ ] 관리자 정보: `payment_failed` 주문 행에는 해당 주문의 실패 금액·시각·안전한 실패 사유가 있고, 실패 상태가 아닌 주문 행에는 해당 정보가 없다.
- [ ] 노출 제한: 결제 실패 응답과 관리자 주문 목록에 카드 정보, 내부 오류, 예외 메시지·스택, 원시 오류 응답이 포함되지 않는다.
- [ ] 테스트 증거: 결제 실패의 상태·HTTP 402·주문/이력 보존·재고 미변경, 재결제 거부, 관리자 노출·비노출을 검증하는 테스트가 통과한다.

### 미정인 기준

- [ ] **미정:** 안전한 실패 사유의 응답·저장·관리자 표시 필드명과 허용 값이 승인된 후, 그 스키마를 검증하는 기준을 추가한다.
- [ ] **미정:** 관리자 노출을 기존 API로 완료로 볼지 별도 UI로 제공할지 승인된 후, 대상 인터페이스의 검증 기준을 추가한다.
- [ ] **미정:** 포함할 재고 시나리오와 결제 시점 재고 부족의 상태·응답이 승인된 후, 각 시나리오별 저장·재고 결과 기준을 추가한다.

## Human Decision Needed

1. “관리자 화면”은 기존 `GET /admin/orders` API의 응답 변경만을 뜻하나요, 아니면 별도 UI를 포함하나요?
2. 결제 실패 응답과 이력·관리자 목록에 저장·표시할 안전한 실패 사유의 필드명과 허용 값은 무엇인가요?
3. `payment_failed` 주문의 재결제를 거부할 때의 HTTP 상태와 응답 메시지는 무엇인가요?
4. “재고 문제”에 주문 생성 시 부족 차단, 동일 상품 수량 합산, 생성 시 미차감, 결제 성공 재검사·한 번만 차감을 모두 포함하나요? 포함할 시나리오를 지정해 주세요.
5. 결제 시점 재고가 부족하면 주문 상태와 결제 응답을 어떻게 처리하나요?
6. 같은 주문에 실패 이력이 여러 개 있을 때 관리자 목록에 표시할 이력의 선택 기준은 무엇인가요?
7. 이 Issue의 우선순위, 납기, 배포 대상과 필수 검증 명령은 무엇인가요?
