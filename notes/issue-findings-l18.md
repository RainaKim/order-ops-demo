## 고객 보고와 사건의 미확인 사항

- Issue와 VOC에 따르면 고객은 첫 결제 실패 뒤 같은 주문의 두 번째 결제가 성공했고 주문 상세에는 결제 완료, 직후 관리자 목록에는 결제실패가 표시됐다고 보고했다. VOC는 첫 토큰이 `FAIL`로 시작했다고도 기술한다 (`labs/fixtures/l18-voc-report.md:3-12`). 이는 고객 보고이지 독립적으로 검증된 실행 기록이 아니다.
- 실제 두 요청의 주문 ID와 동일 주문 여부, 실행 환경·버전·프로세스, 요청 시각 및 각 응답, 각 시점의 주문 상태·결제 이력·재고, 주문 상세와 관리자 조회 원본, 두 번째 응답과 저장 결과의 일치 여부, 재현 조건은 미확인이다. Issue와 참고 자료에 해당 기록이 없고 사건 환경에 접근하거나 실행하지 않았기 때문이다.
- `src/store.ts:37-49`의 현재 저장소는 프로세스 메모리이며 초기화 시 주문과 시도 기록이 지워진다. 따라서 현 로컬 저장소만 읽어 과거 사건의 기록이 보존됐다고 가정할 수 없다.

## 정책상 확인된 기준

- `docs/order-policy.md:19-44,53-77`: 실패 주문과 이력을 보존하고, `payment_failed`에서 같은 주문의 재결제 성공이나 `pending` 복귀는 금지한다. 관리자 목록은 저장된 주문의 현재 상태를 표시하며 실패 이력만으로 다른 상태를 덮어쓰지 않는다. 실패 정보는 `payment_failed`에만 연결하고, 상태와 이력 불일치는 임의 대체하지 않는다.
- `docs/payment-policy.md:9-23`: 결제 실패에는 HTTP 402와 안전한 실패 정보·이력이 필요하다. `payment_failed` 재결제 거부 시 기존 상태와 이력은 바뀌지 않는다. 네트워크·인프라 수준의 기술적 재시도는 별도 보류 사항이다.
- `docs/inventory-policy.md:9-15,30-36`: 주문 생성 시 미차감, 결제 성공 확정 전 재검사와 한 번의 차감이 기준이다. 결제 실패나 `payment_failed` 재결제 거부 시 재고를 차감하거나 복원하지 않는다. 결제 시 재고 부족의 상태·응답과 환불 후 재고 복원은 보류다.
- `docs/order-policy.md:75-89`: 같은 주문에 실패 이력이 여러 개일 때 표시할 이력의 선택 기준은 사람의 결정이 필요하다. 카드 정보·내부 오류·원시 오류는 관리자 목록에서 제외한다. 이 사건에 여러 실패가 있었다는 뜻은 아니다.

## 현재 코드와 테스트의 정적 관찰

- `src/server.ts:1-11`은 주문·결제·관리자 라우터를 연결한다. `src/orders.ts:43-61,80-105`는 품목별 수량을 합산해 재고를 확인하고, 충분하면 재고 차감 없이 `pending` 주문을 저장하며 상세 조회에서 저장 주문을 반환한다.
- `src/payments.ts:22-40,97-145`에서 유효한 `pending`, 양수 금액 주문만 결제할 수 있다. `FAIL` 토큰은 실패 이력을 추가하고 `payment_failed`로 바꾸며 402 `{ ok: false }`를 반환한다. 이후 같은 실패 주문은 결제 가능성 검사에서 현재 코드상 400으로 거부된다. 이 분기는 새 이력과 재고 변경 전에 반환한다. 성공 경로는 재고 검사 후 차감, `paid` 변경 및 성공 이력 기록을 수행한다.
- `src/admin.ts:20-25,42-60,67-72`는 저장 주문을 순회하지만 해당 주문에 실패 시도가 하나라도 있으면 저장 상태 대신 `결제실패`를 반환한다. 실패 상세는 저장 상태가 `payment_failed`일 때만 제공한다. 그러므로 실패 이력과 다른 저장 상태가 함께 존재한다면 표시가 정책과 다를 수 있다. 이것만으로 실제 사건에서 그러한 데이터가 존재했거나 이 코드가 실행됐다고 증명할 수 없다.
- `src/admin.ts:28-39`는 현재 실패 이력을 시각 내림차순으로 선택한다. 정책은 복수 실패 이력의 선택 기준을 미결로 두므로, 기존 구현과 테스트를 승인된 장기 기준으로 간주하지 않는다.
- `tests/orders.test.ts:147-204`는 실패 주문·이력 보존과 재고, 재결제 거부 후 상태·이력 개수·재고를 확인하도록 작성되어 있다. 상태 전체와 이력 내용의 전후 동등성까지 확인하는지는 별도 검토가 필요하다.
- `tests/orders.test.ts:318-338`의 저장 상태 표시 검사는 `it.fails`로 작성돼 있고, `:340-400`은 실패 주문의 `결제실패` 표시와 조건부 상세를 기대한다. `:402-463`은 인위적으로 복수 실패 이력을 구성해 최신 이력을 기대하고, `:465-555`는 불완전 이력 오류와 고아 이력 행 미생성을 확인하도록 작성돼 있다. 저장 상태가 `paid` 등인 주문에 실패 이력이 공존하는 경우의 표시 검사는 보이지 않는다. 이들은 테스트 소스의 관찰이며 이번 실행 결과가 아니다.
- `README.md`에는 실패 주문 삭제, 생성 시 재고 차감, 이전 상태 타입 등 현재 코드와 다른 설명이 남아 있다. 현재 동작 판단에는 코드와 테스트를 사용했다. 정책 문서에도 과거 구현 설명이 남아 있으므로 정책의 규범과 현재 제공 여부 설명을 구분한다.

## 가설과 확인 방법 — 원인 미확정

| 가설 | 확인 방법 및 한계 |
| --- | --- |
| 사건 당시 저장 상태가 `paid`이고 같은 주문에 실패 이력이 있어 관리자 파생 표시가 덮어썼을 수 있다. | 사건 시각의 주문·이력·관리자 응답과 실행 버전을 연결해 대조한다. 격리된 테스트에서 해당 상태와 실패 이력을 명시적으로 구성해 표시를 관찰할 수 있지만, 그 재현만으로 사건 원인은 증명되지 않는다. |
| 두 요청이 서로 다른 주문 또는 실행 환경에서 처리됐거나 당시 버전이 현재 코드와 달랐을 수 있다. | 민감 정보를 제외한 요청 상관 ID, 주문 ID, 배포 버전·프로세스와 시각을 비교한다. 실제 자료가 없으면 미확인으로 남긴다. |
| 두 번째 성공 응답과 저장 결과가 일치하지 않았을 수 있다. | 두 번째 응답 원본과 직후 저장 상태·이력·상세 조회를 동일 환경과 시각 기준으로 대조한다. 현재 자료는 어느 방향의 불일치도 입증하지 않는다. |

사건 확인 시 카드 토큰과 고객 식별 정보는 기록하지 않는다. 격리 재현을 하더라도 실제 주문 재처리나 외부 결제 호출은 하지 않는다.

## Planner handoff

1. 사건 자료의 확보 가능 여부를 확인하고 위 미확인 항목과 이유를 유지한다. 현재 코드의 정상 순차 경로는 실패 후 동일 주문의 성공을 설명하지 못하므로 사건과 분리해 검토한다.
2. 사람에게 사건의 운영 처리, 이번 Issue의 변경·제외 범위, 관찰 가능한 상태·응답·저장 결과와 검증 증거를 결정받는다. 재결제 금지는 이미 승인된 정책이며 재선택할 사항이 아니다. 응답의 미결 세부 값은 추측하지 않는다.
3. 범위에 복수 실패 이력 선택이나 보류된 재고·기술적 재시도 상황이 들어가면 필요한 정책 결정을 먼저 요청한다. 정책 충돌 또는 근거 부족이 발견되면 구현 전에 중단한다.
4. 결정 후 `docs/templates/implementation-plan.md`로 요청과 승인 근거, 변경 후보, 테스트, 위험 및 중단 조건을 연결한다. 관리자 저장 상태와 실패 이력 공존, 실패 주문 보존, 재결제 거부 전후 상태·이력·재고, 실패 상세와 노출 제외를 검증 후보로 검토하되 범위와 기대 결과는 사람의 결정에 맞춘다. 계획 Approval Gate 충족 전 `src/`와 `tests/`를 수정하지 않는다.
