## Goal

사건의 고객 보고와 확인 사실·미확인을 구분하고, 관리자 표시와 실패 주문 재결제 거부에 관한 정책 근거를 기록한다. 사건의 운영 처리, 이번 변경·제외 범위와 관찰 가능한 상태·응답·저장 결과 및 검증 증거를 사람이 결정한 뒤 이 계획을 확정한다. 현재 사건 자료나 실행 결과가 없어 사건 원인과 구현 완료를 판정할 수 없다.

## Steps

### Step 1 — 사건 근거와 사람 결정 확보

- 입력 근거: Issue의 조사 및 사람 결정 요구, 탐색 기록.
- 허용된 변경: 승인된 범위의 조사 기록과 계획 정리만. 실제 주문 재처리 및 외부 결제 호출 금지.
- 종료 상태: 요청·응답, 동일 주문 여부, 실행 환경·버전, 각 시점의 상태·이력·재고·관리자 조회와 재현 조건을 확인하거나 자료 부재 이유와 함께 미확인으로 기록. 운영 처리, 범위·제외, 완료 기준과 검증 증거를 사람이 결정.
- 확인 방법: 민감정보를 제외한 사건 자료와 정책·코드를 대조하고 결정의 승인자와 기록 위치를 남긴다. 자료 확보가 불가능하면 미확인으로 유지한다.

### Step 2 — 승인된 범위만 구현 (조건부)

- 입력 근거: Issue의 확정 정책 및 Step 1에서 기록한 사람 결정과 승인된 계획.
- 허용된 변경: 승인 후 이 표의 변경 대상과 책임을 구체화한 범위만. 미결 응답 값이나 복수 실패 이력 선택 기준은 추측하지 않는다.
- 종료 상태: 사람이 승인한 관찰 가능한 상태·응답·저장 결과를 만족한다.
- 확인 방법: 아래 승인된 검증을 먼저 실행하고 diff를 Issue·정책·결정과 대조한다. 사건 재현만으로 실제 원인을 확정하지 않는다.

### Step 3 — 검증과 handoff (조건부)

- 입력 근거: 승인된 완료 기준, 테스트 및 저장소 검증 순서.
- 허용된 변경: 승인된 범위의 검증 및 결과 기록. PR draft는 향후 `notes/pr-draft-l18.md`에 인계하며 현재 생성하지 않는다.
- 종료 상태: 승인된 테스트와 `npm test`, `npm run lint`, `npm run typecheck`의 결과 및 미실행 사유·잔여 위험이 기록된다.
- 확인 방법: 테스트 결과와 diff를 확인하고 실패 또는 미결 사항을 사람에게 보고한다.

### 사람에게 필요한 결정

1. 사건 자료를 어디에서 확보할 수 있으며 확보할 수 없다면 미확인 상태로 어떤 운영 판단을 할 것인가? 실제 상태·이력을 확인한 뒤 필요한 주문 운영 처리는 무엇인가?
2. 이번 Issue에 관리자 표시 수정과 재결제 거부 회귀 검증 중 무엇을 포함하고 어떤 후속 작업을 제외할 것인가? 각 상태·응답·저장 결과의 관찰 가능한 완료 기준과 검증 증거를 승인해 달라. 재결제 거부 응답의 세부 값은 무엇인가?
3. 범위에 복수 실패 이력 선택이 필요하다면 어떤 이력을 표시할 것인가? 기술적 재시도나 재고 부족 등 보류 상황이 필요하다면 해당 조건·결과를 어떻게 결정할 것인가? 각각은 해당 범위에 포함될 때만 결정이 필요하다.

### Approval Gate

- 승인 근거: 없음. 승인자·승인 기록 위치와 구체적 범위·완료 기준이 필요하다.
- [ ] 계획과 필요한 결정이 승인되기 전에는 `src/`와 `tests/`를 수정하지 않는다.
- 재개 시 최신 Issue와 결정 근거를 확인하고 이 계획의 파일·단계·테스트를 확정한 뒤 승인 기록을 남긴다. 승인 전 implementer에 넘기지 않는다.
