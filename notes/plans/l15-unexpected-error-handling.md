## Goal

관리자 조회와 결제 처리에서 예기치 못한 예외가 발생하면 승인된 `500` 내부 오류 응답(`{ ok: false, error: "internal_error", requestId }`)을 반환하고, 요청을 추적할 수 있는 서버 오류 정보를 `console.error`에 보존한다. 정상 결제와 정상 관리자 조회가 계속 동작함을 검증한다.

## Steps

### Step 1 — 승인된 내부 오류 응답과 보존 적용

- 입력 근거: 사람이 승인한 외부 응답 `500`, `{ ok: false, error: "internal_error", requestId }` 및 `console.error` 보존 항목. 중복된 `code`는 사람 승인에 따라 제거함
- 허용된 변경: 두 catch에서 빈 배열·기본 응답 fallback을 제거하고, 오류 종류·requestId·주문 ID·처리 단계·메시지·스택·전후 상태·발생 위치를 `console.error`에 남김
- 종료 상태: 예기치 못한 예외가 `500`과 승인된 본문으로 응답되며 주문 상태·재고·결제 이력의 의미를 새로 정하지 않음
- 확인 방법: 테스트에서 각 catch를 의도적으로 발생시키고 응답·`console.error` 인수를 검증

### Step 2 — 정상·예외 경로 테스트

- 입력 근거: 승인된 오류 처리 경계와 현재 정상 결제 테스트
- 허용된 변경: 결제 예외, 관리자 조회 예외, 정상 관리자 조회 assertion 추가
- 종료 상태: 두 예외 경로의 외부 응답과 서버 보존이 검증되고, 정상 결제·정상 관리자 조회가 통과함
- 확인 방법: `npm test`, `npm run lint`, `npm run typecheck`

## Risks

| 위험 | 영향 | 감지 방법 |
| --- | --- | --- |
| 예외를 `402` 또는 `payment_failed`로 오인 | 정책 밖 상태 전환·이력 생성 | 예외 테스트에서 주문 상태·이력·재고 불변성 확인 |
| 내부 오류가 외부 본문에 노출 | 정책의 민감 정보 노출 금지 위반 | 정확한 외부 본문 assertion |
| 로그 문맥 누락 | 장애 추적 불가 | `console.error` 인수 assertion |
