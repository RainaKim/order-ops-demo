## Goal

`GET /admin/orders`가 저장된 `payment_failed` 주문에만 운영 판단용 결제 실패 금액·시각·안전한 사유를 제공하고, 다른 주문이나 민감한 결제·내부 오류 정보를 노출하지 않도록 하는 구현 계획이다.

기존 구현 승인과 2026-10-17 reviewer 판정을 아래 Approval Gate에 연결한다. 처음에는 후속 수정을 두 문서로 한정했으나, 사용자가 이어서 수용 항목의 실제 수정을 지시했다. 따라서 해당 항목에 필요한 `src/admin.ts`와 `tests/orders.test.ts` 수정도 수행한다.

## Confirmed Facts

- 주문 정책은 관리자 목록의 기준을 `orders`에 보존된 주문으로 정하고, `order.status === "payment_failed"`일 때만 실패 금액·시각·사유를 제공하도록 한다. 보통 주문에는 빈 값·추정값을 붙일 수 없다.
- 기존 구현에서 `PaymentAttempt`에 안전한 실패 사유 `payment_declined`가 추가되었다.
- 기존 `deriveDisplayStatus()`는 실패 시도가 하나라도 있으면 `'결제실패'`를 파생한다. 호출을 복원했으며 정책 상태와의 불일치는 다음 실습으로 인계한다.
- 현재 `payment_failed` 주문은 재결제가 금지되어 정상 API 흐름으로는 추가 실패 이력이 생기지 않는다. 그러나 정책은 같은 주문에 복수 실패 이력이 있을 때 관리자 표시 대상으로 어느 이력을 고를지 사람의 결정을 요구한다.
- 카드 토큰·카드 식별 정보, 내부 오류·예외 메시지·스택, 원시 오류 응답은 관리자 목록에 포함하면 안 된다.

## Steps

### Step 1 — 승인된 안전한 실패 사유의 저장 경계 추가

- 입력 근거: 승인된 사유 코드 `payment_declined`.
- 허용된 변경: `src/store.ts`, `src/payments.ts`.
- 종료 상태: 실패 결제 시도는 금액·시각과 함께 `payment_declined`만 저장한다. 카드 토큰, 카드 식별 정보, 내부 예외·스택, 원시 오류 본문은 저장하지 않는다.
- 확인 방법: 실패 결제 뒤 저장된 `PaymentAttempt`의 `reason: 'payment_declined'`와 금지 값의 부재를 테스트한다.

### Step 2 — 저장 상태 기반의 조건부 실패 정보 구성

- 입력 근거: 주문 정책의 관리자 조회 기준, 최근 실패 이력 선택, 승인된 500 불일치 처리 계약.
- 허용된 변경: `src/admin.ts`의 관리자 행 타입·변환·해당 주문의 이력 조회. `deriveDisplayStatus()`의 기존 호출을 복원하고 함수 본문·시그니처를 보존한다.
- 종료 상태: 모든 저장 주문이 `id`, `status`, `totalKrw`, `createdAt`을 제공하고, 저장된 주문 상태가 `payment_failed`인 행만 최근 완료 실패 이력의 `paymentFailure: { amountKrw, at, reason }`을 제공한다. 실패 정보의 조건은 저장 상태를 사용한다. 표시 상태는 기존 `deriveDisplayStatus()` 호출을 유지하며 정책과의 불일치는 다음 실습에 인계한다.
- 확인 방법: pending·paid·payment_failed 주문을 함께 조회해 실패 정보의 조건부 제공과 주문별 이력 결합을 별도 일반 테스트로 검증한다. 기존 정책 상태 감시 테스트는 `it.fails()`로 복원한다.

### Step 3 — 데이터 불일치와 민감 정보 방어 검증

- 입력 근거: 주문 정책의 완전한 실패 정보 요구·고아 이력 금지, 승인된 `internal_error` 불일치 처리 계약.
